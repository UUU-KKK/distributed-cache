### 3.1 存储内核与 TTL 过期

【要写的要点】
1. 数据结构选择：`OrderedDict` 存"key → 条目"，条目里放 `value / expire_at / freq / seq`。
2. 为什么用 `time.monotonic()` 而不是墙上时钟：单调递增、不受系统时间调整影响。
3. **两种删除时机**（这是重点）：
   - **惰性删除**：读的时候发现已过期，顺手删掉；
   - **后台主动清扫**：一个常驻线程每 1 秒扫一遍，把过期条目清掉。
   为什么要两个都要？惰性删除省 CPU 但过期条目会占内存；定期清扫保证"内存不被过期数据白占"——对应题目"内存受限"要求。
4. `ttl(key)` 返回值的约定（-1 表示永不过期，-2 表示不存在/已过期）。
5. 统计口径：hits / misses / expirations / evictions / hit_rate。

【可用素材】
- 测试：`test_cache_store.py` 19 项，其中 TTL 相关 4 项。
- 现场证据（运行 `verify_replication.py` 或 `fault_experiments.py` 实验1 都能看到）：

```

           节点 expirations 计数：0 -> 1
```
- 后台清扫的日志证据：`[node-1] 后台清理 1 条过期数据`（跑节点时会打印）。

### 3.2 淘汰策略：LRU 与 LFU

【要写的要点】
1. **为什么需要淘汰**：内存受限（题目明确要求），容量满了必须腾位置。
2. **LRU（最久未使用先淘汰）**：
   - 实现：`OrderedDict` + 每次访问 `move_to_end`，淘汰时弹出最左边那个；
   - 复杂度：读/写 O(1)；
   - 适合什么：访问有"时间局部性"的场景（刚用过的还会再用）。
3. **LFU（使用频次最少先淘汰）**：
   - 实现：每个条目记 `freq` 访问次数，另配一个全局递增的 `seq` 序号做"平局裁决"（频次相同时淘汰更早进入的）；
   - 复杂度：本项目为 O(n) 扫描（实现简单、可读；真实系统会用 O(1) 的频次桶）；
   - 适合什么：访问有"频次局部性"的场景（少数热点长期被访问）。
4. **两者对比**（自己写一句取舍：LRU 更新知识快、抗不了"偶发批量扫描"；LFU 保护长期热点、但新数据难以上位——这正是我们要在报告里如实说明的取舍）。
5. 淘汰时机的一个细节：**先清理过期条目，再淘汰**——避免"为了给新数据腾地方，却误淘汰了一条本来还活着的数据"。

【可用素材】
- 测试：LRU 4 项 + LFU 3 项 + "过期优先清理"2 项。
- 实测断言原文（可截图）：
```
[PASS] LRU：淘汰最久未使用的 b
[PASS] LRU：最近使用过的 a 仍在
[PASS] LFU：淘汰访问次数最少的 c
[PASS] LFU：高频的 a 仍在
[PASS] 过期优先清理：new1 未被误淘汰
```
- 参数：命令行 `--policy lru|lfu`、`--capacity N`。

### 3.4 分布式：容灾与异步复制

【要写的要点】
1. **为什么需要副本**：单机缓存一份数据，进程一挂/重启就全没了；多副本是最基础的容灾手段；也对应"内存受限"下用多机分担容量。
2. **同步复制 vs 异步复制**（这是核心取舍，务必写清）：
   - 同步：写完要等所有副本确认，写延迟 = 最慢副本的延迟；任一副本卡住，写入就卡住。
   - 异步：本地写完立刻返回，抄送交给后台；写延迟稳定，但有"不一致窗口"。
   - 我们的选择：**异步**，依据是题目明确"**数据丢失部分可接受**"。
3. **实现方式（三个细节，都是加分点）**：
   - **队列 + 单个后台线程**：PUT/DELETE 只做"入队"（微秒级）就返回，发货由独立线程完成——为什么必须是**单**线程？保证 FIFO 顺序，避免"先删后写"乱序到达导致副本数据错乱。
   - **复制风暴避免**：副本节点收到 `/replicate` 后**只写本地、不再向外转发**，传播只发生一跳。否则 node-1→node-2→node-3→node-1 会无限循环。
   - **最终一致性**：因此测试必须**轮询等待**而不是立即断言（异步的本质）。
4. **已知边界（如实写，不要藏）**：
   - 副本离线时那次抄送只记账（`repl_sent_fail`），**不重试**；
   - 节点重启后，停机期间缺失的数据**不会自动补齐**（我们不做反熵修复）；
   - 节点像阶段4 那样接了数据源时，缺失数据会被"回源"重新取到——那是另一层兜底（见 4.2 的"两段式实验"）；
   - 不做并发写冲突解决（没有 CAS、没有版本比较），见 5.8；
   - 不支持在线迁移与扩容，见 5.9。

【可用素材】
- 实测（现场证据，可截图）：


### 3.5 回源与缓存击穿保护

【要写的要点】
1. **数据源（origin）是什么**：真实系统里就是数据库。它被显式建模成两个可调参数——`--delay`（单次查询耗时）与 `--parallel`（并发处理上限），并带一个访问计数器。**要说清"为什么要故意做慢"**：① 真实数据库本来就有查询延迟和并发上限，慢是如实建模；② 毫秒级的危害肉眼看不见，放大成几百毫秒才能测得出来、讲得清楚。这段适合写进"实验设计"。
2. **回源**：缓存未命中时去数据源取，取到后写进缓存（并顺手复制给副本），再返回给客户端。
3. **缓存击穿（cache stampede）**：热点 key 一过期，多个并发请求同时发现"缓存没有"，一起穿透到数据源，把数据库打爆。
4. **解决方案 singleflight（请求合并）**：
   - 概念对：**领跑者**（真正去回源的那一个）与**搭车者**（等待并共享结果）；
   - 只合并"**时间上重叠**"的请求（错开的请求那时通常已命中缓存，各查各的）；
   - 按 **key 粒度**合并（查 A 的不会阻塞查 B 的）；
   - **失败也共享**：领跑者失败时，所有等待者收到同一个错误（而不是各自再去打已经出问题的数据库），之后可以重新发起。
   - 崩溃安全：用 `Event` + `finally` 清理注册表，避免"领跑者异常后搭车者永远卡住"。
5. 与复制的配合：回源取到的数据也会入复制队列，因此副本最终也能拿到。

【可用素材】
- 实测对照（**报告里最有力的一组数据**）：

| 配置 | 20 个并发请求的结果 | 数据源被访问次数 | 最慢响应 |
|---|---|---|---|
| 有保护（默认） | 20/20 成功 | **1 次** | **0.22 秒** |
| 无保护（`--no-singleflight`） | 20/20 成功 | **20 次** | **4.09 秒** |

- 测试：`test_singleflight.py` 11 项（20 并发只执行 1 次、5 个 key 各合并各的、错误共享、出错后可重试、错开的调用不合并）
  + `test_stampede.py` 12 项（有保护回源 1 次 vs 无保护 20 次、第二次读命中缓存不回源）。
- 参数：`--with-origin`（集群带数据源启动）、`--origin-delay 0.2`、`--no-singleflight`（对比组）。

### 4.2 故障注入实验：预测 → 实测 → 对照 → 解释

2. 我们的实现：`fault_experiments.py` 全自动脚本，自己启动/杀掉/重启 1 个数据源 + 3 个节点，每个实验依次打印四段。
3. **实验设计的关键决策（这段最有含金量）——为什么要分段隔离**：
   - 初版实验（所有节点都接着数据源）中，实验 1~3 的预测**全部落空**；
   - 排查结论：**不是代码 bug，而是阶段4 的"回源"把阶段3 的"复制缺口"兜住了**——笔记 TTL 过期/副本缺失的读请求，都被回源自动补上，于是"缺口"在观测层面消失了；
   - 于是改成三段式：**实验 1~3 在不接数据源的纯缓存集群上跑**（隔离阶段1~3 的行为），**实验 4~5 重启集群并接上数据源**（验证阶段4），**实验 6~11 再切回纯缓存集群做故障注入**（分区 / 重复 / 乱序 / 时钟回拨 / 热点 key / 响应丢失）；
   - 这背后是实验设计的基本功——**控制变量**（想测某一层，就要把其它层当干扰源先关掉）；
   - 改版后：十一个实验全部与预测一致。
4. **这一节要诚实写"我们预测错了一次"**——它不是减分项，恰恰是课程要的"预测→实测→对照→解释"的真实循环。

## 五、设计取舍与已知边界

【要写的要点】这一节是"成熟度"的体现，主动写比被问出来好得多。逐条说明"我们做了什么、没做什么、为什么、代价是什么"：

1. **异步复制换低写延迟**：代价 = 不一致窗口 + 崩溃时队列内数据丢失。依据：题目"数据丢失部分可接受"。
2. **复制失败不重试、不做反熵修复**：节点离线期间的写入不会补给它；内存缓存重启即清空。（可提一句"真实系统的做法是 WAL / 快照 / Merkle 树反熵，我们未实现"。）
3. **数据源是单点依赖**：它挂掉时，已缓存数据照常命中，但没缓存过的 key 会返回 502。真实系统会加限流、熔断、备用源。
4. **LFU 为 O(n) 扫描**：实现简单可读，规模大时应换成 O(1) 的频次桶。
5. **无数据分片/路由**：每个节点都是全量副本，没有一致性哈希；真集群会用分片来水平扩展容量。
6. **无持久化**：纯内存，进程退出即丢（这本身符合"临时缓存服务"的题目设定）。
7. **单机多进程模拟**：通信语义与真集群一致，但没有真实的跨机网络延迟；分区、重复、乱序都是靠参数在应用层模拟的（`--block` / `--repl-dup` / `--repl-reorder`）。
8. **不做并发写冲突解决：没有 CAS，也没有版本比较**：同一 key 的并发写按"到达副本的先后"覆盖（LWW by arrival）。
   - 代价：并发写会丢更新；客户端重试还可能覆盖别人刚写的新值（实验 11 已实测）；
   - 为什么可接受：这是缓存不是账本，写入是整值覆盖、读多写少，题目允许最终一致与部分丢失；
   - 若要补：每个 key 带 version / `If-Match` 做比较，或给请求加 requestId 去重表；代价是每次写多一次比较与存储，冲突时还要业务决定"拒绝还是合并"；
   - 对应课程提问"删掉版本比较代码会怎样"：我们本来就没有版本比较，所以明确声明"不提供 CAS"，而不是假装有。
9. **不支持在线迁移 / 弹性扩容**：3 个节点固定拓扑，每个节点全量副本；新节点只能空状态启动，之后靠新写入被动补齐。
   - 代价：没有快照传输、迁移状态机与切流；迁移到一半宕机会留下不完整副本，旧数据也不会自动补齐（无反向熵）；容量无法水平扩展；
   - 为什么可接受：题目是临时缓存，允许冷启动丢数据，也未要求在线扩容；
   - 若要补：快照 + 增量日志、迁移状态（pending / ready）、迁移完成后再切读流量、Merkle 树反熵；复杂度会明显上升；
   - 对应课程 topic"新节点在数据迁移一半时宕机"：我们选择不实现迁移，因此该场景不适用，如实说明而不是硬编一个假流程。

### 附录 C：术语表（写报告时统一用词）

| 术语 | 含义 |
|---|---|
| 命中 / 未命中 | 缓存里有 / 没有这条数据 |
| TTL | 存活时间，到期即失效 |
| 惰性删除 / 主动清扫 | 读到才删 / 后台线程定期扫掉 |
| LRU / LFU | 淘汰最久未使用 / 最少使用的数据 |
| 副本 | 同一份数据的另一份拷贝，存在别的节点 |
| 同步 / 异步复制 | 等所有副本确认 / 本地成功即返回，后台抄送 |
| 不一致窗口 | 写完到副本收到之间的时间差 |
| 最终一致性 | 不再有新写入时，各节点数据最终会一致 |
| 复制风暴 | 副本互相转发导致无限循环 |
| 回源 | 缓存未命中去数据源取 |
| 缓存击穿 | 热点 key 失效瞬间，并发请求一起穿透到数据源 |
| singleflight / 请求合并 | 同一时刻同一 key 的并发回源合并为一次 |
| 领跑者 / 搭车者 | 真正回源的那一个 / 等待并共享结果的其余请求 |
