## 第 6 页 · 存储内核：数据结构与并发安全

**放什么**
- 数据结构示意：`OrderedDict { key -> {value, expire_at, freq, seq} }`
- 一行说明：`threading.RLock` 保护并发读写

**讲什么**
- 为什么用 `OrderedDict`：LRU 需要"随时把某个 key 移到队尾"，`OrderedDict` 的 `move_to_end` 是 O(1)，天然适合。
- 为什么必须加锁：HTTP 服务是多线程的，多个请求会同时改同一个字典——不加锁会出现"数据错乱"（比如读到一个正在被改到一半的结构）。
- 用 `time.monotonic()` 而不是系统时间：不受系统时钟调整影响。

**备注**：可能会被问"GIL 是不是就不用加锁了"——答：GIL 只保证单条字节码原子，像"判断 + 修改 + 删除"这种复合操作仍需要锁。

## 第 7 页 · TTL 的两种删除时机

**放什么**
两张并排的小图 / 两个格子：
```
惰性删除：读的时候发现过期 → 顺手删掉（省 CPU，但过期条目会占内存）
主动清扫：后台线程每 1 秒扫一遍 → 批量清掉（保证内存不被白占）
```
**讲什么**
- 为什么两个都要：只靠惰性删除，没人读的过期数据会一直占内存——而题目明确"内存受限"。
- 呼应第 2 页的"内存受限"要求。

**备注**：证据可现场跑 `fault_experiments.py` 的实验 1：写入 TTL=2 秒 → 3 秒后 404，且 `expirations` 从 0 变 1。

## 第 8 页 · 淘汰策略（上）：为什么需要 + LRU

**放什么**
- 一句问题："内存满了，新数据来了往哪放？"
- LRU 机制图（时间轴：a → b → c，访问 a 之后 a 跳到队尾，淘汰最左边的 b）

**讲什么**
- LRU = Least Recently Used，"最久没被用过的先走"。
- 实现：`OrderedDict` + 每次访问 `move_to_end`，淘汰时弹出最左边；**读写都是 O(1)**。
- 适用：访问有时间局部性（刚用过的还会再用）。

---

## 第 9 页 · 淘汰策略（下）：LFU 与两者对比

**放什么**
对比表：
| | LRU | LFU |
|---|---|---|
| 淘汰谁 | 最久未使用 | 访问次数最少 |
| 实现 | OrderedDict + move_to_end | freq 计数 + seq 平局裁决 |
| 复杂度 | O(1) | 本项目 O(n) 扫描 |
| 优势 | 跟进新热点快 | 保护长期热点 |
| 短板 | 偶发批量扫描会冲掉热点 | 新数据难以上位（历史包袱）|

**讲什么**
- LFU 的 `seq` 是什么：全局递增序号，用来做平局裁决——频次相同时淘汰更早进来的那个。
- 一句取舍："我们两种都实现了，用 `--policy` 切换；规模大了 LFU 应换成 O(1) 的频次桶。"
- 一个细节：**先清过期、再淘汰**——避免为了腾地方误淘汰还活着的数据。

**备注**：证据是 `test_cache_store.py` 里 `[PASS] LRU：淘汰最久未使用的 b`、`[PASS] LFU：淘汰访问次数最少的 c` 这两组断言。

## 第 12 页 · 异步复制：队列 + 单线程

**放什么**
流程图（第一版那张）：`客户端 → node-1 → 复制队列 → 后台发货线程 → 副本`

**讲什么**
- 写入只做"入队"（微秒级）就返回 200，发货交给**后台单线程**。
- **为什么必须是单线程**：保证 FIFO 顺序——避免"先删后写"乱序到达副本，导致副本最终数据是错的。
- **为什么用队列**：解耦。如果 PUT 里直接发 HTTP，就又变回同步复制了。

## 第 14 页 · 复制风暴与避免

**放什么**
- 错误做法：`node-1 → node-2 → node-3 → node-1 → …`（无限循环箭头）
- 正确做法：`node-1 → node-2`、`node-1 → node-3`（只一跳，副本收到后只写本地）

**讲什么**
- "如果副本收到数据后又转发给别人，就会无限循环、流量爆炸——这叫复制风暴。"
- "我们的规则：**只有最初收件的节点负责发货，副本只入库、不转发。**"

## 第 15 页 · 复制的边界：缺口不补 + 故障验证

**放什么**
实验 3 的真实输出（三个对照点）：
```
① 杀掉 node-3 后：node-1/node-2 照常读写        -> 集群没有单点
② node-1 复制台账：sent_ok=5, sent_fail=1       -> 发往死节点的失败被记账
③ 重启 node-3 后：新数据 200（有）、旧数据 404（没有） -> 缺口不会自动补
```
**讲什么**
- 三条结论：高可用成立 / 失败有记账 / **缺口不补**。
- "最终一致"是有边界的：它只保证"**在线节点**最终拿到数据"，不保证"离线节点能补上历史亏空"。
- 呼应题目"数据丢失部分可接受"。

**备注**：主动说边界会显得很成熟。如果老师追问"怎么办"，答"WAL / 快照 / Merkle 树反熵，我们未实现"。

## 第 16 页 · 缓存击穿：问题

**放什么**
- 击穿示意图（20 个箭头全部穿透到数据源）
- 数据源的三个"脾气"：慢（0.2 秒）、一次只处理 1 个查询、带访问计数器

**讲什么**
- 讲清事故：热点 key 一过期，并发请求**同时**发现没有 → 全部穿透到数据库 → 数据库被打爆。
- **说清"为什么故意把数据源做慢"**（这页很适合展示你的实验设计意识）：① 真实数据库本来就有延迟和并发上限，慢是如实建模；② 毫秒级的危害看不见，放大到几百毫秒才测得出来。

## 第 23 页 · 设计取舍与已知边界

**放什么**
取舍表（做了什么 / 没做什么 / 为什么）：
| 取舍 | 代价 | 依据 |
|---|---|---|
| 异步复制 | 不一致窗口；崩溃丢队列内数据 | 题目允许"数据丢失部分可接受" |
| 复制失败不重试 | 离线节点缺口不补 | 简化实现；真实系统用 WAL/反熵 |
| 数据源单点 | 它挂了则新 key 返回 502 | 未做限流/熔断/备用源 |
| LFU 为 O(n) | 规模大时慢 | 换来实现简单可读 |
| 无分片路由 | 每节点都是全量副本 | 未做一致性哈希 |
| 无持久化 | 退出即丢 | 题目就是"临时缓存服务" |

**讲什么**
- "这些不是遗漏，是我们有意识的取舍。"逐条一句话带过，**主动坦白比被问出来强**。

|---|---|
| 为什么用异步而不是同步复制？ | 同步会让写延迟被最慢副本拖住；题目明确"数据丢失部分可接受"，所以我们用异步换稳定延迟 |
| 节点崩了会怎样？ | 队列中未发出的操作会丢（`repl_sent_fail` 记账）；重启后停机期间的旧数据不会自动补——这是已知边界 |
| 不一致窗口多久？ | 可配置（`--repl-delay`），默认接近瞬时；真实网络通常毫秒级，我们人为放大到 2 秒便于演示 |
| singleflight 和加锁有什么区别？ | 加锁是排队后各自再执行一遍；我们是把同一瞬间的重复请求**合并成一次执行、结果共享**，且只合并时间重叠的 |
| 为什么把数据源做慢？ | 真实数据库本来就有延迟与并发上限；放大后才可测量、可演示 |
| LRU 和 LFU 哪个好？ | 看访问模式：LRU 跟进新热点快，LFU 保护长期热点但新数据难上位；我们都实现了可切换 |
| 这算真分布式吗？ | 单机多进程模拟，通信与故障语义一致；差别是没有真实网络分区与跨机延迟，已写入报告边界 |
| 67 项断言全过就没问题了吗？ | 只说明我们写下的预期都成立；未实现的重试、反熵、分片都在报告"已知边界"里 |
