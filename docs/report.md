## 摘要

本文实现了一个三节点的分布式临时缓存服务：单机侧提供 TTL 过期、LRU/LFU 淘汰、回源与请求合并，集群侧通过异步复制在节点之间同步数据。系统用 Python 标准库实现，每个节点是独立进程、通过 HTTP 通信，不依赖任何第三方运行时库。我们为它编写了 67 项自动断言和 11 个故障注入实验，覆盖节点宕机、网络分区、消息重复与乱序、时钟回拨、热点 key、响应丢失等场景。实验表明：异步复制在保证低写延迟的同时存在可观测的不一致窗口；请求合并把 20 个并发回源压缩到 1 次；而缺少版本比较与在线迁移则是本设计明确接受的边界。

## 一、需求分析与选题说明

场景 8 要求实现一个分布式的临时缓存服务。把原始要求拆开，可以得到五条硬约束：

1. 服务是**临时缓存**，不是持久化存储；
2. **数据丢失部分可接受**，这为复制策略留出了取舍空间；
3. 必须支持 **TTL**，数据到期自动失效；
4. **内存受限**，容量满了必须有淘汰策略；
5. 需要多节点协作，具备基本的容灾能力。

课程同时点明了四个技术重点，它们恰好对应缓存系统从内到外的四层：

| 课程重点 | 对应章节 | 主要实现文件 |
|---|---|---|
| 过期（TTL） | 3.1 | src/cache_store.py |
| LRU / LFU（淘汰） | 3.2 | src/cache_store.py |
| 异步复制 | 3.4 | src/replication.py、src/cache_node.py |
| 缓存击穿 | 3.5 | src/singleflight.py、src/origin.py |

选择这个场景的理由是：这四个重点不是四个孤立的功能，而是一条完整链路——先有存储内核，再有单机服务，然后是多副本，最后是高并发下的回源保护。每往上一层，都会引入新的失败模式，也正好能用课程要求的故障注入方法逐层验证。

其中"数据丢失部分可接受"这一条最关键。它直接决定了我们敢用异步复制：客户端写入只等本地成功，副本由后台慢慢抄送。代价是存在不一致窗口，源节点崩溃时队列里的数据会丢。如果要求零丢失，就必须换成同步复制或共识协议，写延迟和实现复杂度都会高一个量级。

## 二、总体架构设计

系统分为三层，每层只依赖下一层：

- **存储层 `CacheStore`**：纯内存的缓存内核，负责 TTL、LRU/LFU 淘汰和命中统计，不涉及网络。
- **网络层 `CacheNode`**：把存储包装成 HTTP 服务，处理读写删除、回源、请求合并和副本接收。
- **分布式层**：多个 `CacheNode` 进程 + 异步复制发送器 + 模拟数据源，组成一个三节点集群。

一次读请求有两条路径。命中时，`CacheNode` 直接返回存储层的值，并附上剩余 TTL；未命中且配置了数据源时，先由 singleflight 决定是"领跑者"还是"搭车者"，领跑者回源取数、写入本地、把这次写入放进复制队列，然后返回。写请求则先写本地，再把复制任务入队，立即向客户端返回 200。

技术选型上有三个决定：

- **Python**。标准库自带 `http.server`、`queue`、`threading`，不用任何框架就能把分布式语义演示清楚，答辩时也可以逐行讲。
- **单机多进程**。每个节点是独立 Python 进程，占独立端口，通过 HTTP 通信。课程允许用任何可行方式模拟分布式系统；把"多台机器"换成"同一台机器上的多个独立进程"后，通信与故障语义保持一致，阶段 5 可以真的把进程 kill 掉。
- **运行时零第三方依赖**。整个项目只需要 Python 标准库即可启动，降低了复现成本。

文件组织如下：

```
distributed-cache/
├── src/
│   ├── cache_store.py     存储内核：TTL / LRU / LFU / 统计
│   ├── cache_node.py      网络层：HTTP 服务 + 回源 + 请求合并
│   ├── replication.py     异步复制（每副本一条队列 + 独立线程）
│   ├── singleflight.py    请求合并器
│   └── origin.py          模拟数据源（慢查询 + 并发上限 + 访问计数）
├── tests/                 5 套测试，共 67 项断言
```

## 三、核心机制详解

### 3.1 存储内核与 TTL 过期

存储用 `OrderedDict` 保存 `key -> 条目`。每个条目包含四个字段：`value`（值）、`expire_at`（到期时刻）、`freq`（访问次数，供 LFU 使用）、`seq`（全局递增序号，用于频次相同时的平局裁决）。

**过期时间用单调时钟记录。** 默认时钟是 `time.monotonic()`，它只增不减，不受系统时间被手动修改或 NTP 回拨的影响。这一点在第 9 个实验中做了对照验证：把墙钟拨回 60 秒后，墙钟节点的 TTL 从 59.5 秒变成 119.5 秒，而单调时钟节点的 TTL 保持不变。

过期条目有**两种删除时机**：

- **惰性删除**：读请求发现 `expire_at` 已过，顺手删除并返回未命中。它省 CPU，但如果某个 key 再也不被访问，就会一直占着内存。
- **后台主动清扫**：一个常驻线程每秒扫描一遍，把过期条目清掉。它保证"内存不被过期数据白占"，对应题目"内存受限"的要求。

两者缺一不可：只有惰性删除会浪费内存，只有定期清扫则会让读请求读到已经过期的数据。

`ttl(key)` 的返回值沿用 Redis 的约定：正数表示剩余秒数，`-1` 表示永不过期，`-2` 表示 key 不存在或已过期。统计口径包括 `hits`、`misses`、`expirations`、`evictions` 和 `hit_rate`，可以通过 `/stats` 实时查看。

实测证据（实验 1）：写入 TTL=2 秒的数据，刚写入时返回 200，3 秒后返回 404，节点的 `expirations` 计数从 0 变成 1。后台清扫的日志也能看到 `[node-1] 后台清理 1 条过期数据`。

### 3.2 淘汰策略：LRU 与 LFU

容量满时必须腾位置，这是题目"内存受限"的直接要求。我们实现了两种策略，用 `--policy lru|lfu` 切换。

**LRU（最久未使用先淘汰）**：利用 `OrderedDict` 的有序性，每次读写都把 key `move_to_end` 移到队尾，淘汰时弹出队首。读、写、淘汰都是 O(1)。它适合有时间局部性的访问模式——刚用过的数据大概率还会再用。

**LFU（使用频次最少先淘汰）**：每个条目记录 `freq`，每次命中加一；淘汰时找 `freq` 最小的条目。频次相同时用全局 `seq` 裁决，淘汰更早进入的那个，避免"新数据永远选不出来"。本项目的 LFU 是 O(n) 扫描，实现简单、便于讲解；真实系统会用频次桶做到 O(1)。

两者的取舍很明确：LRU 对新数据友好、适应访问模式变化快，但扛不住一次偶发的批量扫描——扫描会把一堆只用一次的数据顶到队尾，把真正的热点挤出去；LFU 能保护长期热点，但新数据在频次追上来之前很难存活，存在"历史包袱"。我们没有做 LRU-K 或 W-TinyLFU 这类折中方案，因为在本项目的规模下收益不明显。

还有一个容易忽略的细节：**淘汰前先清过期**。如果直接按 LRU 淘汰，可能为了给新数据腾位置，却误淘汰了一条本来还活着的数据，而旁边正好躺着一条早就过期的。所以 `set` 在容量满时先调用一次过期清理，再决定淘汰谁。

测试覆盖：LRU 4 项、LFU 3 项、"过期优先清理"2 项。典型断言包括"淘汰最久未使用的 b、最近使用过的 a 仍在""淘汰访问次数最少的 c、高频的 a 仍在"。

### 3.3 网络接口设计

节点对外是一个 HTTP + JSON 服务。选 HTTP 的理由很实际：跨进程、跨机器都能调，用 curl 就能验收，不需要自己设计协议和序列化格式。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /health | 健康检查，返回节点 ID 和运行时长 |
| GET | /stats | 统计指标（存储 + 复制 + 回源 + 请求合并） |
| GET | /dump | 导出全部数据，调试用 |
| GET | /cache/{key} | 读取，未命中且配置了数据源时自动回源 |
| PUT | /cache/{key} | 写入，body 为 `{"value": ..., "ttl": 60}` |
| DELETE | /cache/{key} | 删除 |
| POST | /replicate | 接收副本写入，集群内部使用 |

数据源侧另有 `/data/{key}`、`/health`、`/stats` 和 `/reset` 四个接口，其中 `/reset` 用于在对照实验前清零访问计数。

请求处理使用 `ThreadingHTTPServer`，每个请求一个线程。多个线程会同时读写同一个 `OrderedDict`，因此存储层用 `RLock` 保护。这里用可重入锁而不是普通锁，是因为 `set` 内部可能调用 `_purge_expired`，两者都需要持锁。

返回码约定：200 成功，404 不存在，400 请求体非法，502 回源失败。另外把 TCP 等待队列调大到 64（`request_queue_size = 64`），避免并发压测时连接排队被误读成服务变慢。

### 3.4 分布式：容灾与异步复制

单机缓存的问题很直接：进程一挂或一重启，内存里的数据就全没了。多副本是最基础的容灾手段，同时也让多台机器分担容量。

**同步复制与异步复制的取舍**是这一节的核心。同步复制要求写完等所有副本确认，写延迟等于最慢副本的延迟，任一副本卡住写入就卡住；异步复制只等本地成功，副本由后台抄送，写延迟低，但存在不一致窗口，源节点崩溃时未发出的数据会丢失。

我们选择异步复制，依据就是题目里"数据丢失部分可接受"。具体实现是：PUT 在本地 `set` 成功后，把 `{op, key, value, ttl, origin}` 放进复制队列，立刻返回 200；后台线程逐条 POST 到副本的 `/replicate`。

实现过程中有两个值得记录的修正。

**第一，每个副本一条独立队列。** 最初的版本是"一条队列 + 一个后台线程"，所有副本共用。做分区实验时发现：node-3 被隔离后，发往它的连接要等 2 秒超时，排在其后的 node-2 消息也被一起堵住，健康副本的复制被故障副本拖慢。改成每个副本一条队列、一个专用线程后，node-3 被隔离时 node-2 仍能在 16 毫秒内收到数据。每个副本内部仍是单线程，所以"同一副本按产生顺序收到操作"这个保证没有丢。

**第二，复制报文携带的是剩余 TTL，而不是原始 TTL。** 最初直接把客户端传入的 `ttl` 转发给副本，副本收到后从当前时刻重新起算。把复制延迟调成 2 秒后就能看到：源节点的数据只剩 4 秒，副本却还有 6 秒，同一份数据在两个节点上寿命不同。修复方式是在入队时记录时间，真正发送时用 `ttl - 排队耗时` 重算剩余时间，副本按剩余值写入。这样即使消息被延迟、被乱序缓冲区压住，副本的过期时刻也与源节点一致。

还有一个防复制风暴的细节：副本收到 `/replicate` 后只写本地，不再向外转发。否则 node-1 → node-2 → node-3 → node-1 会无限循环。

由于是异步复制，**最终一致性只能用轮询验证，不能立即断言**。实测：写入 node-1 后立刻读 node-2 返回 404；等 3 秒再读返回 200，`ttl` 为 28.9。node-1 的复制指标显示 `repl_enqueued=1`、`repl_sent_ok=2`（两个副本各一次）。

### 3.5 回源与缓存击穿保护

真实系统里缓存背后是数据库。我们把数据源显式建模成两个可调参数：`--delay`（单次查询耗时）和 `--parallel`（并发处理上限），并带一个按 key 统计的访问计数器。

**为什么要故意把数据源做慢？** 两个原因。第一，真实数据库本来就有查询延迟和并发上限，慢是如实建模，不是人为制造问题。第二，毫秒级的危害肉眼看不见——20 个并发打到数据库，如果每次只要 1 毫秒，总耗时也只差 19 毫秒，测不出来也讲不清楚；把单次查询放大到 200 毫秒，危害就变成了 0.22 秒和 4.09 秒的差别。

**缓存击穿**指的是：热点 key 一过期，多个并发请求同时发现缓存没有，一起穿透到数据源，把数据库打爆。

解决方案是 singleflight（请求合并），核心是一对概念：**领跑者**真正去回源，**搭车者**等待并共享结果。四条规则：

1. 只合并**时间上重叠**的请求。错开的请求到达时，领跑者通常已经把数据写进缓存，后来的请求直接命中，各查各的，不需要合并。
2. 按 **key 粒度**合并。查 A 的请求不会阻塞查 B 的。
3. **失败也共享**。领跑者失败时，所有等待者收到同一个错误，而不是各自再去打已经出问题的数据库；失败后注册表被清理，下一次请求可以重新发起。
4. **崩溃安全**。用 `Event` 通知等待者，并在 `finally` 里清理注册表，避免领跑者异常后搭车者永远卡住。

回源取到的数据也会进入复制队列，所以副本最终也能拿到，不需要各自回源。

实测对照（20 个并发请求同一个未缓存的 key）：

| 配置 | 结果 | 数据源被访问次数 | 最慢响应 |
|---|---|---|---|
| 有保护（默认） | 20/20 成功 | 1 次 | 0.22 秒 |
| 无保护（`--no-singleflight`） | 20/20 成功 | 20 次 | 4.09 秒 |

两者都返回了正确结果，差别只在数据源承受的压力和尾延迟。这正是击穿保护的价值：它不改变正确性，改变的是系统在热点失效瞬间的存活能力。

## 四、实验与验证

### 4.1 测试体系：67 项自动断言

断言是测试里"自动判对错"的一句话，不成立就报错中断。项目里用一个 `check(name, condition)` 小函数实现，输出 `[PASS]` 或 `[FAIL]`。

测试分两类。**单元测试**单独测零件：存储内核和请求合并器不启动网络，直接调函数。**集成测试**把零件装起来路测：真的启动节点、真的发 HTTP、真的等复制。两类都需要——单元测试定位快，集成测试才能发现"单独都对、装起来出错"的问题。

| 测试文件 | 测什么 | 类型 | 断言数 |
|---|---|---|---|
| test_cache_store.py | TTL / LRU / LFU / 统计 | 单元 | 19 |
| test_singleflight.py | 请求合并器 | 单元 | 11 |
| test_cache_node.py | 存储 + HTTP 服务 | 集成 | 13 |
| test_replication.py | 3 节点异步复制 | 集成 | 12 |
| test_stampede.py | 节点 + 数据源 + 并发 | 集成 | 12 |
| **合计** | | | **67** |

每次改代码后五套全部重跑。一个真实的例子：阶段 4 改了 `cache_node.py` 的读逻辑（未命中不再直接返回 404，而是先尝试回源），这会影响阶段 1~3 的测试预期，所以必须回归。后来重构复制发送器、修改 TTL 传递方式时也一样，67 项全过是每次提交前的底线。

但要清醒：67 项全过只说明"我们写下的预期都成立"，不等于系统没有 bug。它覆盖的是我们想到的场景，想不到的场景只能靠故障注入去撞。

### 4.2 故障注入实验：预测 → 实测 → 对照 → 解释

课程要求的方法论是四步：预测系统行为、运行故障注入、对照预测和实际结果、解释违反了哪项保证或者为什么仍然正确。

我们把它做成了一个全自动脚本 `fault_experiments.py`：自己启动数据源和 3 个节点，按顺序执行 11 个实验，每个实验先打印预测，再打印实测数据，最后给出对照结论和解释。全程约 110 秒，可以现场运行。

**这一节最重要的不是 11 个实验本身，而是我们第一次做错了。**

初版实验里，所有节点都接着数据源。结果实验 1~3 的预测全部落空：

```
初版实测（节点接了数据源）：
  实验1 3 秒后读：HTTP 200（预测 404）    <- 过期数据被回源刷新
  实验2 立刻读副本：HTTP 200（预测 404）  <- 复制缺口被回源补上
  实验3 重启后读旧数据：HTTP 200（预测 404）<- 缺口被回源填回
```

排查后确认不是代码 bug，而是阶段 4 的"回源"把阶段 3 的"复制缺口"兜住了：所有本该暴露缺口的读请求，都被自动回源补上了，于是缺口在观测层面消失。

改法是分段隔离：实验 1~3 在不接数据源的纯缓存集群上跑，实验 4~5 重启集群并接上数据源，实验 6~11 再切回纯缓存集群做故障注入。背后是实验设计的基本功——**控制变量**：想测哪一层，就要把其它层当干扰源先关掉。改版后 11 个实验全部与预测一致。

| 实验 | 预测 | 实际 | 结论 |
|---|---|---|---|
| 1 TTL 到期 | 写入 200 → 3 秒后 404，expirations+1 | 完全一致 | 与预测一致 |
| 2 不一致窗口 | 立刻读副本 404；延迟后再读 200 | 完全一致 | 与预测一致 |
| 3 杀副本 | 集群照常服务；复制失败记账；重启后缺口不补 | sent_fail=1；重启后旧数据 404、新数据 200 | 与预测一致 |
| 4 杀数据源 | 已有缓存 200；新 key 502 | 完全一致 | 与预测一致 |
| 5 击穿对照 | 回源 1 次 vs 约 20 次 | 1 次 / 0.22 秒 vs 20 次 / 4.09 秒 | 与预测一致 |
| 6 双向分区 | node-2 秒级收到；node-3 与反向都读不到；两侧分叉 | node-2 16ms 收到；node-3 404；node-1/2 也 404；丢弃 1/2 条 | 与预测一致 |
| 7 重复投递 ×3 | 发送 6 次，副本状态与单次相同 | sent_ok=6；两个副本值均为 dup-ok | 与预测一致 |
| 8 乱序到达 | 10 条全部到达，顺序与写入不同 | 10/10 到达，顺序确实被打乱 | 与预测一致 |
| 9 时间回拨 | 墙钟 TTL 多 60 秒，单调时钟不变 | 59.5→119.5 秒 vs 59.5→59.5 秒 | 与预测一致 |
| 10 热点 key | 50% 流量下读不慢，写侧放大 | 200/200 成功；60 次写复制 120 次（共 3 份） | 与预测一致 |
| 11 响应丢失 | 客户端报错但已写入；盲目重试覆盖新值 | RemoteDisconnected；node-1 已是 v1；重试后 B 的 b-v2 丢失 | 与预测一致 |

几个值得单独说的结果：

**实验 6（双向分区）** 用 `--block` 让两侧的复制消息直接丢弃。node-3 被隔离后，写入 node-1 的数据 16 毫秒就到达 node-2，但 node-3 读不到；反过来写入 node-3 的数据，node-1 和 node-2 也读不到。两侧各自可读可写，数据分叉。这是我们选择 AP 的直接代价：可用性没有下降，但没有人能裁定哪边是对的，而且因为没有反熵，分区恢复后分叉会一直保留。

**实验 7（重复投递 ×3）** 验证的是幂等性。同一条写入被投递 3 次，两个副本共成功发送 6 次，但副本最终值和只发一次完全相同。原因是 `set` 是整值覆盖，天然幂等。这个实验也解释了为什么购物车那类"数量 +1"的场景不能直接照搬这套复制——非幂等操作重复执行就会翻倍。

**实验 9（时间回拨）** 用 `--clock wall` 启动一个墙钟节点作对照。写 ttl=60，然后把墙钟拨回 60 秒：墙钟节点的剩余 TTL 从 59.5 秒涨到 119.5 秒，数据凭空"续命"；单调时钟节点保持 59.5 秒。这就是"为什么不能只用物理时钟"的直接证据：TTL 会算错，如果用时间戳做 LWW 冲突解决，更旧的写入还会被误判为更新。

**实验 11（响应丢失）** 用 `/admin/fault` 让服务端写成功后不回响应、直接断开。客户端收到 `RemoteDisconnected`，但 node-1 实际已经写入 v1；用相同值重试后，服务端处理了 2 次（复制入队 2 次），结果仍然正确。随后做危险场景：A 写入后响应丢失，B 写入 b-v2，A 盲目重试 a-v1，最终值是 a-v1，B 的更新被覆盖。这说明"重试安全"不能靠"值相同"来保证，必须靠 requestId 去重或版本比较。

## 五、设计取舍与已知边界

这一节主动说明"我们做了什么、没做什么、为什么、代价是什么"。

1. **异步复制换低写延迟**。代价是不一致窗口和崩溃时队列内数据丢失。依据是题目"数据丢失部分可接受"。
2. **复制失败不重试、不做反熵修复**。节点离线期间的写入不会补给它，重启后缺失的数据也不会自动补齐。真实系统的做法是 WAL、快照或 Merkle 树反熵，我们未实现。接数据源时，缺失数据会被回源补上，但那是另一层兜底，不是复制层的能力。
3. **数据源是单点依赖**。它挂掉时，已缓存的数据照常命中，没缓存过的 key 返回 502。真实系统会加限流、熔断和备用源。
4. **LFU 为 O(n) 扫描**。实现简单可读，规模大时应换成 O(1) 的频次桶。
5. **无数据分片与路由**。每个节点都是全量副本，没有一致性哈希，容量无法水平扩展。
6. **无持久化**。纯内存，进程退出即丢，这符合"临时缓存服务"的设定。
7. **单机多进程模拟**。通信语义与真集群一致，但没有真实的跨机网络延迟；分区、重复、乱序都是靠参数在应用层模拟的（`--block`、`--repl-dup`、`--repl-reorder`）。
8. **不做并发写冲突解决：没有 CAS，也没有版本比较**。同一 key 的并发写按"到达副本的先后"覆盖（LWW by arrival）。代价是并发写会丢更新，客户端重试还可能覆盖别人刚写的新值（实验 11 已实测）。之所以可以接受：这是缓存不是账本，写入是整值覆盖、读多写少，题目允许最终一致与部分丢失。若要补，可以给每个 key 带 version 或 `If-Match` 做比较，或给请求加 requestId 去重表；代价是每次写多一次比较与存储，冲突时还要业务决定"拒绝还是合并"。课程提问"删掉版本比较代码会怎样"——我们本来就没有版本比较，所以这里明确声明"不提供 CAS"，而不是假装有。
9. **不支持在线迁移与弹性扩容**。3 个节点固定拓扑，每个节点全量副本；新节点只能空状态启动，之后靠新写入被动补齐。没有快照传输、迁移状态机与切流，迁移到一半宕机会留下不完整副本，旧数据也不会自动补齐，容量无法水平扩展。之所以可接受：题目是临时缓存，允许冷启动丢数据，也未要求在线扩容。若要补，需要快照 + 增量日志、pending/ready 迁移状态、完成后再切读流量、Merkle 树反熵，复杂度会明显上升。课程 topic"新节点在数据迁移一半时宕机"因此不适用，如实说明而不是硬编一个假流程。

## 六、总结与体会

<!-- 这一段请按你的真实经历改写。下面是可以直接用的事实素材，不要照抄成套话。 -->

这个项目里我最初最不理解的是"为什么要异步复制"。直觉上，写完等所有副本确认才叫可靠，异步听起来像偷工减料。真正想通是在做实验 2 的时候：写入 node-1 后立刻读 node-2 是 404，等 3 秒再读是 200。那一刻我才意识到，分布式系统里"写成功"和"所有副本都有"本来就是两件事，异步只是把这两件事的间隔摆到了明面上。题目允许部分丢失，所以这个间隔是可以接受的。

第二个想通的是"为什么要把数据源做慢"。一开始觉得是故意制造麻烦，后来发现如果不做慢，击穿保护的收益只有十几毫秒，既测不出来也讲不清楚；把单次查询放大到 200 毫秒，0.22 秒和 4.09 秒的对比才成立。实验设计里，"把效应放大到可观测"本身就是一个设计动作。

我认为这个项目里最巧妙的设计是 singleflight 里的"领跑者/搭车者"。它没有引入任何新组件，只是在请求入口加了一个按 key 的等待表，就把 20 次并发回源压成 1 次，而且失败也能共享，不会出现"数据库已经挂了，20 个请求还在轮流打它"。

最大的收获来自一次做错的实验。初版故障实验里，所有节点都接着数据源，结果前三个实验的预测全部落空。当时第一反应是代码有 bug，排查后才发现是回源把复制层的缺口补上了。那次之后我才真正理解"控制变量"不是实验课的口号：想观测哪一层，就必须把其它层的兜底关掉，否则你看到的永远是最后一层的行为。

如果继续做，下一步会按这个顺序补：复制失败重试与启动时的反熵（解决重启缺口）、requestId 去重（解决响应丢失后的盲目重试）、数据分片（解决容量扩展）、最后才是持久化。前三项都是在现有结构上加法，分片则要动路由层，成本最高。
